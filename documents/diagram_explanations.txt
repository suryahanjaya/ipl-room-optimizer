### 4. System Workflow

The architecture diagram shows two parallel execution paths that converge at the Processing Engine layer.

**Web path:**
1. The University Admin opens a web browser and navigates to `localhost:5000`.
2. The Flask Web Server serves the HTML page.
3. The user uploads an Excel or CSV file via `POST /api/upload`.
4. The user selects a mode (Fast or Deep) and triggers `POST /api/merge`.
5. The server spawns a background thread that launches the optimizer as a subprocess.
6. The browser polls `GET /api/status/<task_id>` to track progress.
7. The Pipeline Controller reads the input file, partitions data, and routes each group to the appropriate solver.
8. Results are written to an Excel workbook in `results/`.
9. The server parses the Excel output into JSON and returns it to the browser.
10. The user views results and optionally downloads the Excel file via `GET /results/<filename>`.

**CLI path:**
1. The user runs `python src/ipl_optimizer.py -i input.xlsx -o output.xlsx` from a terminal.
2. The `main()` function parses arguments and calls `process_exam_data()` directly.
3. The same Pipeline Controller logic executes.
4. Results are written to the specified output path.

Both paths share the same Processing Engine and Infrastructure layers.

### 7. Key Technical Observations

- **Dual-interface architecture.** The system provides two independent entry points (web and CLI) that both converge on the same optimization pipeline. This is a clean separation of interface from logic.
- **Adaptive solver selection.** The pipeline controller uses a size threshold to decide between the exact solver and the heuristic. This is a practical design choice — exact MILP is too slow for large datasets, while the heuristic sacrifices optimality for speed.
- **Automatic degradation.** If the MILP solver fails (timeout or error), the system catches the exception and falls back to the greedy heuristic. This ensures the process never stalls.
- **Subprocess isolation.** The web server runs the optimizer as a subprocess rather than calling Python functions directly. This isolates the optimization workload from the Flask process and enables real-time stdout-based progress tracking.
- **File-based data exchange.** The system uses local file storage (`uploads/`, `results/`) instead of a database. Input and output are Excel workbooks. There is no database present in the codebase.
- **No authentication.** The Flask server does not implement login, session management, or access control. It is designed for local or trusted-network usage.

### 4. System Workflow

Based on the component diagram, the internal workflow operates as follows:

**Via Web Interface:**
1. `run.py` imports the Flask `app` object from `src/web/server.py` and starts the server.
2. `server.py` serves `index.html`, which loads `app.js` and `app.css`.
3. When the user uploads a file, `upload_file()` saves it to `uploads/`.
4. When the user starts merging, `merge()` spawns a background thread running `optimization_worker()`.
5. `optimization_worker()` invokes `src/ipl_optimizer.py` as a subprocess with the appropriate command-line arguments.
6. Inside the subprocess, `main()` parses arguments and calls `process_exam_data()`.
7. `process_exam_data()` calls `identify_column()` and `validate_room_data()` during data preparation.
8. For each (shift, campus) group, the function instantiates either `MILPRoomOptimizer` (if group size ≤ threshold) or `GreedyBinPacker` (if group size > threshold).
9. If `MILPRoomOptimizer.solve()` raises an exception, the pipeline catches it and falls back to `GreedyBinPacker`.
10. `generate_output_reports()` converts solver results into report data structures.
11. The pipeline writes results to `results/` as a multi-sheet Excel workbook.
12. Back in the main process, `optimization_worker()` calls `export_results_to_json()` to parse the Excel output into JSON.
13. The JSON is stored in `TASK_STATUS` and returned to the browser on the next poll.

**Via CLI:**
1. The user calls `main()` directly from the terminal.
2. Steps 6–11 above execute identically.
3. Optionally, the user runs `show_summary.py` or `export_to_json.py` as separate post-processing steps.

### 7. Key Technical Observations

- **Monolithic optimizer module.** The primary optimization logic — both solvers, the pipeline controller, report generation, utilities, and the CLI — all reside within a single file (`ipl_optimizer.py`, 878 lines). This is functional but could become difficult to maintain as the system grows.
- **Strategy Pattern for solver selection.** The pipeline controller dynamically selects between `MILPRoomOptimizer` and `GreedyBinPacker` based on the `size_threshold` parameter. Both solvers share the same input/output interface (accept rooms/subjects/students/capacities lists and return assignment/open_rooms/metadata tuples), enabling interchangeable use.
- **Retained legacy code.** `src/core/merging.py` is an older implementation with its own full pipeline. It is present in the codebase but is **not imported or used** by any other module in the active system. Its functions (`solve_group_greedy()`, `solve_group_exact_milp_pulp()`) were refactored into the class-based design of `ipl_optimizer.py`.
- **Decoupled utility scripts.** `show_summary.py` and `export_to_json.py` operate as standalone post-processing tools. They read the result Excel files independently and are not called by the main pipeline. However, the web server's `export_results_to_json()` duplicates the logic of `export_to_json.py` with enhanced detail (room-level merge tracking).
- **In-memory task state.** The web server uses a global Python dictionary (`TASK_STATUS = {}`) to track task progress. This state is not persisted — restarting the server loses all task history. This design is appropriate for single-user, local use.
- **No external database.** The system uses only the local file system for data persistence. There is no SQL or NoSQL database in the codebase.

- The Welcome Page is displayed with the HCMUT logo and an "Enter Application" button.
- Clicking the button calls `enterApplication()` in `app.js`, which hides the welcome page and shows the main application.

**Step 2 — Upload Data File**
- The user drags and drops an `.xlsx` or `.csv` file, or clicks the upload button to select a file.

- `uploadFile()` sends the file to the server via `POST /api/upload` as multipart form data.
- The server's `upload_file()` handler saves the file to `uploads/input_data.{ext}`.
- The server responds with `{ success: true, filepath: "..." }`.
- The UI updates to show the uploaded file name and size.

**Step 3 — Select Mode and Start Optimization**
- The user selects either "Fast Mode" or "Deep Optimization".
- The user clicks the "Start Merging" button.
- `startMerging()` in `app.js` sends a `POST /api/merge` request with `{ filepath, mode }`.
- The server's `merge()` handler creates a UUID task ID, initializes `TASK_STATUS[task_id]`, and spawns a daemon thread running `optimization_worker()`.
- The server responds immediately with `{ success: true, task_id: "..." }`.

**Step 4 — Background Processing**
- `optimization_worker()` constructs a subprocess command: `python -u src/ipl_optimizer.py -i <input> -o <output> --verbose [mode-specific flags]`.
- For Fast Mode: `--threshold 0` (forces greedy for all groups).
- For Deep Mode: `--threshold 200 --time-limit 600` (prefers MILP for groups ≤ 200 rooms).
- The subprocess starts. `process_exam_data()` executes inside it.
- The pipeline reads the input file, identifies columns, validates data, and groups rows by (shift, campus).
- For each group, it selects and runs the appropriate solver.
- Progress is printed to stdout as `Processing [i/N]: shift=..., campus=..., rooms=...`.
- The worker thread reads stdout line by line and extracts progress via regex matching.
- It updates `TASK_STATUS[task_id]` with the current percentage and message.

**Step 5 — Poll for Progress**
- `pollTaskStatus()` in `app.js` sends `GET /api/status/<task_id>` every 1 second.
- The server returns the current `{ status, progress, message, result }` from `TASK_STATUS`.
- The UI updates a progress bar and status message in real time.
- When `status` becomes `"completed"`, polling stops and the result JSON is passed to the rendering functions.

**Step 6 — View Results**
- `showResults()` in `app.js` receives the JSON data containing overall statistics and per-shift/campus detail objects.
- Summary cards display: Initial Rooms, Final Rooms, Rooms Saved, Efficiency %.
- `filterAndRender()` populates shift and campus dropdown filters from the data.
- `createDetailCard()` renders a card for each shift/campus group showing kept rooms (green tags) and removed rooms (red tags).
- Clicking a room tag calls `showRoomDetail()`, which displays a popup with the room's subject, student count, capacity, and merge information (which rooms merged into it, or which room it was merged to).
- A "Show Merge Details" button calls `showMergeDetail()` and `createMergeModal()` to display a full merge table.

**Step 7 — Download Results**
- The user clicks the download button.
- The browser requests `GET /results/Result_YYYY-MM-DD_HH-MM-SS.xlsx`.
- The server's `download_result()` handler uses `send_from_directory` to serve the file with `as_attachment=True`.
- The Excel workbook contains sheets: Summary, Summary_ByCampus, Room_Changes_Detail, Groups, Merges, MILP_Stats.

### 5. Technologies and Technical Aspects

- **Single-Page Application (SPA) pattern** — The frontend uses a single HTML page (`index.html`) with multiple sections that are shown/hidden via JavaScript. No page reloads occur during the workflow.
- **Drag-and-drop file upload** — Implemented via HTML5 drag events (`dragover`, `dragleave`, `drop`) handled in `setupEventListeners()` in `app.js`.
- **Asynchronous task processing** — The server uses a background thread + polling pattern instead of WebSockets or Server-Sent Events. The client polls every 1 second.
- **Real-time progress via stdout parsing** — The background worker reads the subprocess stdout line by line and uses `re.search(r"Processing \[(\d+)/(\d+)\]:", line)` to extract progress numbers.
- **Mode-dependent parameter configuration** — Fast Mode sets `threshold=0` (bypasses MILP for all groups). Deep Mode sets `threshold=200` and `time_limit=600` (allows up to 10 minutes per MILP solve).
- **Excel multi-sheet output** — Results are written using `pd.ExcelWriter` with the `openpyxl` engine. Six sheets are generated: Summary, Summary_ByCampus, Room_Changes_Detail, Groups, Merges, MILP_Stats.
- **Inter font** — The UI uses Google Fonts Inter (weights 300–800) loaded via external stylesheet.
- **Dark mode** — Toggled via `toggleDarkMode()`, which sets a `data-theme` attribute on the HTML element. Theme preference is stored in `localStorage`.

### 7. Key Technical Observations

- **Two distinct user experiences.** The web interface provides a guided, step-by-step workflow with visual feedback. The CLI provides direct access for users comfortable with terminal commands. Both paths produce identical output files.
- **Polling-based progress tracking.** The system uses a client-side polling loop (1-second interval) instead of WebSockets or Server-Sent Events. This is simpler to implement but generates continuous HTTP requests during processing. The server parses subprocess stdout lines using regex to extract progress percentages.
- **Mode abstraction.** The "Fast" and "Deep" modes visible in the UI are not separate algorithms — they are parameter presets for the same `process_exam_data()` function. Fast Mode sets `threshold=0`, forcing all groups to use the greedy heuristic. Deep Mode sets `threshold=200` and `time_limit=600`, allowing the MILP solver to run on groups up to 200 rooms with a 10-minute time limit.
- **Client-side filtering.** All result data is sent to the browser in a single JSON payload after optimization completes. Filtering by shift and campus happens entirely in JavaScript (`filterAndRender()`), without additional server requests. This is efficient for the expected dataset sizes.
- **Interactive room exploration.** The frontend provides drill-down capability: users can click individual room tags to see subject codes, student counts, capacity, and merge relationships. This is implemented via dynamically generated popup elements (`showRoomDetail()`) rather than separate pages or API calls.
- **No persistent session state.** The web interface does not use cookies, sessions, or user accounts. Each upload-merge-result cycle is independent. The browser's application state (`appState` object in `app.js`) resets when the page is refreshed.
- **File size limit.** The Flask configuration sets `MAX_CONTENT_LENGTH = 16 * 1024 * 1024` (16 MB), limiting the maximum upload size. The file extension is also validated server-side to accept only `.xlsx` and `.csv`.
